## 1. MHW Seamless Co-op: complete feature & UX documentation

**Source:** Wayback Machine snapshot of the mod's main page, captured 2026-09-24 ([web.archive.org/web/20260924041652/nexusmods.com/monsterhunterworld/mods/8805](https://web.archive.org/web/20260924041652/https://www.nexusmods.com/monsterhunterworld/mods/8805)). The CDX index (`web.archive.org/cdx/search/cdx?url=nexusmods.com/monsterhunterworld/mods/8805&matchType=prefix`) confirms **exactly one snapshot exists**, covering only the `?tab=description` view. This matters: Nexus's mod page is a Next.js SPA, and only the SEO-rendered "About this mod" body was captured server-side — the Posts/Bugs/Logs/Stats/Permissions-table widgets are hydrated client-side from a GraphQL API (`api-router.nexusmods.com`) that was never crawled. Tab **counts** are visible in the server-rendered tab bar — Description · **Files 1** · **Images 8** · **Videos 1** · **Posts 146** · **Bugs 7** · Logs · Stats — but the tab **contents** are not (see §9).

**Identity & versioning (verified).** Author `huntardy`; original upload 20 September 2026, updated once, 21 September 2026; the public-facing version shown in the page's Twitter meta tags is **"1.2"**. Interestingly, the mod's own runtime log reports an internal build string of **`1.0.191.0`** (see §2) — a typical pattern of an internal CI/commit-counter build number that doesn't track the public marketing version shown on Nexus.

**Headline pitch (verbatim):** *"Keep your party together through quests, Expeditions, story moments, and time back in town."* / *"Your friend posts a quest. You come along. Less time at the quest board. More time playing together."*

**Full feature list (verbatim from the page):**
- **Join automatically** — follow posted quests, Investigations, and Expeditions without finding the listing yourself.
- **Start story quests together** — join before the leader reaches the cutscene that normally unlocks multiplayer.
- **Share the story** — watch the leader's story cutscenes with your party.
- **Catch up to a hunt in progress** — join a friend's active session; the mod handles quest joining and departure.
- **Land at the same camp** — match the leader's chosen campsite.
- **See your party in town** — shared presence in Astera and the Research Base.
- **Choose who you follow** — host-only (default) or "follow anyone's quest."

**Toggleable settings ("Make it your co-op"), with defaults:** Auto-follow the host (**ON**), Match the host's campsite (**ON**), Bypass the cutscene gate (**ON**), Watch the leader's cutscenes (**ON**, "an open menu is closed after a 30-second wait when needed for playback"), See the party in town (**ON**, "everyone needs this enabled"), Use a voucher when joining (**OFF**), Follow anyone's quest (**OFF**). Settings persist in `nativePC/plugins/mhw-seamless-coop-settings.txt` and survive updates.

**Controls:** F11 toggle panel, F5 cycle panel pages (party/timeline → settings → diagnostics), F2/F3 select/toggle a setting, **F10** = "request a join to the host's quest from town" (explicitly stated not to abandon a quest you're already on).

**Installation/compatibility model:** Standalone — extracted directly beside `MonsterHunterWorld.exe`; **no dependency on Stracker's Loader**, though it is compatible with it and *reuses Stracker's `nativePC/plugins` folder convention* for familiarity. Packaged for Vortex. Explicitly supports **DLL-chaining** other `xinput9_1_0.dll`-based mods via `xinput9_1_0.chain.dll`. Steam Deck/Linux is "untested"; the page suggests the Proton launch option `WINEDLLOVERRIDES="xinput9_1_0=n,b" %command%`.

**Safety model:** a save backup is copied into `nativePC/plugins/mhw-seamless-coop-backups` *before* the mod loads each session, the 10 most recent kept; the page states twice, emphatically, "This mod has never written your save and still does not." On an unsupported game build the mod shows an in-panel **"MOD DISABLED"** state with a reason rather than risk operating against unknown memory layouts.

**Testing-coverage disclaimer (verbatim):** *"Testing has focused on two-player groups. Three- and four-player parties and Iceborne content have had less coverage; reports from those sessions are especially useful. This mod does not advertise an increased hunter limit."*

**FAQ highlights:** friends without the mod cannot benefit from seamless features (full party must match mod version — mismatched versions are "highlighted in red" in the panel); it does **not** replace Steam multiplayer — *"It uses the game's existing quest systems and Steam lobby features. Join the same online session first"*; departure is only forced automatically when following a leader already in the field (if the leader is still in town you "join and ready up normally"); the mod "checks the game code it relies on" each launch and self-disables on unsupported builds.

**Credits:** Built with **MinHook** ([TsudaKageyu/minhook](https://github.com/TsudaKageyu/minhook)) and **Dear ImGui** ([ocornut/imgui](https://github.com/ocornut/imgui)); their licenses are bundled in the release. No explicit statement of the author's own permission terms (asset-use/modification/conversion) was present in the archived text — see §9.

## 2. Source code / architecture (verified vs. inferred)

**No source code exists publicly.** Extensive GitHub searches found nothing: `search_code` for `"mhw-seamless-coop"`, `"mhw-seamless-coop-settings"`, `"mhw-mod-loader"`, and `"xinput9_1_0.chain"` all returned **zero results**; `search_repositories` for `mhw-seamless-coop` returned zero. A GitHub user `huntardy` does exist (id 36344661, [github.com/huntardy](https://github.com/huntardy)), but it has **no discoverable public repositories** (`search_repositories query:"user:huntardy"` fails GitHub's validation check, which GitHub returns specifically for accounts with no indexable repos) — and nothing on the Nexus page itself links to a GitHub account (only `buymeacoffee.com/Huntard` is given), so this username match is **unverified and possibly coincidental**. A Reddit account `huntardy` likewise has essentially no footprint: the only comment found via the pullpush.io mirror is a single 2012 *World of Warcraft* subreddit comment, unrelated to modding. **This is a closed-source, compiled-DLL mod**, consistent with essentially every other mod in this ecosystem (see the "Iceborne Community Edition" / "Skippable Cutscenes" precedent in §6, which is explicitly non-redistributable).

**However, exceptionally detailed behavioral evidence exists.** The mod's own support process asks bug-reporters to attach `mhw-seamless-coop.log`; two real user session logs were found as public GitHub Gists, shared for troubleshooting: [gist.github.com/coallungs/8a85a63b1913d98eb85be54f78104a7c](https://gist.github.com/coallungs/8a85a63b1913d98eb85be54f78104a7c) and [gist.github.com/coallungs/03efeecfd604d2efb89005b58ee7b525](https://gist.github.com/coallungs/03efeecfd604d2efb89005b58ee7b525) (same session started 2026-09-20, "current" vs. "previous" log pair). These are **not source code**, but they are verbatim runtime output, and I treat every quoted line below as **verified**; my grouping of hooks into subsystems and explanation of *why* each exists is **inference**, albeit high-confidence given the self-describing names and observed runtime values.

**Module layout (verified via log banner).** Everything — loader, overlay, settings, and "mod core" — lives in **one DLL**, loaded as the mod's own `xinput9_1_0.dll` (a classic DirectInput-era DLL-proxy injection vector still functional because the game still probes for that filename). The log states outright: *"Overlay, settings and the mod core are all in this DLL; the core does the following and joining, through Steam lobby data and the game's own functions."* Startup sequence from the log: resolve paths → load `coop.toml` (optional; defaults used if absent, in the sampled sessions) → open `mhw-seamless-coop.log` → install **d3d11/d3d12 Present/ResizeBuffers/ExecuteCommandLists hooks** for the Dear ImGui overlay → install ~**40 MinHook detours** into the game executable itself (not into any official API — MHW has none) → go "passive" waiting for a board/scan/join event.

**Engine reality check — the single most important architectural fact for the Wilds port.** Monster Hunter World runs on a customized, late-generation **MT Framework** build, *not* RE Engine; RE Engine only began with Resident Evil 7 (2017) and was first used for a mainline Monster Hunter title with **Rise** (2021), carrying into **Wilds** (2025) (confirmed via multiple sources, e.g. [wccftech.com](https://wccftech.com/capcom-mt-framework-monster-hunter-world/), [MYCPLUS](https://www.mycplus.com/game-development/game-engines/mt-framework/)). **REFramework does not and cannot support MHW** for exactly this reason. This is *why* every hook in huntardy's log is anchored to a raw executable offset (`caller=MHW+0x25C348`, `MHW+0x1B438B9`, `MHW+0x1F2C541`, `MHW+0x1AD9E1F`, `MHW+0x1B106D1`, `MHW+0x1141D24`, etc.) rather than a named managed type — the author had to signature-scan the shipped binary and hard-code detours, Ghidra/IDA-reverse-engineer raw struct layouts (e.g. logged flag fields like `+0C=00000008 +14=0000001B +1261C=00800200`), and re-verify all of it on every patch. This fragility is almost certainly the mechanical basis for the "checks the game code it relies on, disables itself if unsupported" behavior.

**The ~40 verified hook names** (quoted directly from both logs, each logged as `"<name> hook: MH_OK"` at startup via what looks like a table-driven `InstallHook(name) → log result` helper — a pattern worth copying):
`accept_quest`, `set_pending_quest`, `request_member_quest`, `board completion` + `source copy`, `board state11`, `prepare transition`, `prepare mode`, `prepare init`, `GetPlayer`, `DepartStatus`, `player state`, `prepare update` ("preparation observer: 8/8 sites installed"), `network error dialog`, `prepare set state`, `jump to field`, `set depart ready`, **`cutscene gate`**, **`cutscene request`**, **`cutscene watched list`**, `quest hold release`, `quest ForceEvent release`, `quest SealUIInput release`, `expedition: depart`, `expedition: lobby start`, and a large `hub:` family — `player packet receive`, `equip apply`, `interval apply`, `palico packet receive`, `palico stage test`, `palico create write`, `palico action write`, `shared stage test`, `interval write`, `join sync write`, `action write`, `create write`, `spawn request`, `remove player`, `avatar build` — plus `before sync`, `sync receive`, and `fast travel packet`.

**Reconstructed subsystems (inference, from the names + runtime log evidence):**

- **Automated join/departure pipeline** — `accept_quest`/`set_pending_quest`/`request_member_quest`/`board completion`/`board state11`/`prepare *`/`GetPlayer`/`DepartStatus`/`set depart ready`/`jump to field` collectively **script the exact sequence of engine calls a human triggers by hand at the quest board**, end to end. The log shows this literally: a `board state11` state machine walks `0→2→4→5`, a `prepare mode`/`prepare init` struct is populated (`flags=060500DA`, `members=0`, `rows=[-1,-1,-1,-1]`), then `player state` flips, then `lobby start: record quest=305`, then a raw **`native quest accept`** call fires with the real quest ID and a hex dump of the quest definition struct. This is direct, verified confirmation of the FAQ's claim that the mod "uses the game's existing quest systems" rather than inventing its own.
- **Cutscene gate bypass** — three dedicated hooks (`cutscene gate`, `cutscene request`, `cutscene watched list`) plus two UI-unlock hooks (`quest ForceEvent release`, `quest SealUIInput release`). This strongly implies MHW's native restriction is a **per-player "watched cutscenes" table** gated by a check function (the "gate"), and that a forced-camera/locked-input state ("Seal") is what actually prevents a client from being warped into a host's in-progress instance. The mod appears to patch the gate check and release the input seal rather than touch cutscene *playback* itself. The documented "an open menu is closed after a 30-second wait" behavior for shared cutscenes is consistent with the mod detecting a blocking UI state and force-closing it so the scripted join/teleport can proceed.
- **Steam lobby coordination — VERIFIED, not just inferred.** The log contains the line `published coop_post="109775242246465825;1789966454"` immediately after a player posts a quest — a lobby-ID;timestamp pair, written the instant a quest is posted. This is strong direct evidence the mod coordinates **purely through Steam Lobby (and very likely per-member Lobby *Member* data)** — exactly matching the FAQ's "Steam lobby features" claim — with **no custom P2P packet protocol**. The companion diagnostic `"peers: N in the session, N running the mod"` (logged repeatedly) requires a per-member marker visible to every client, which is the idiomatic use of `SetLobbyMemberData`/`GetLobbyMemberData` (my inference for the exact API, though the *existence* of the mechanism is verified by the log). A `"MHW lobby-create phase"` state machine (`phase 0→2→3→4→5`, `result=0/1`, a 17-digit Steam Lobby ID once assigned) matches the shape of Valve's own asynchronous `CreateLobby`/`LobbyCreated_t` flow almost exactly, meaning the mod is observing/driving Steamworks calls the **game itself already makes**, not opening its own sockets.
- **Town/hub presence ("See the party in town")** — the largest hook family (`hub: *`, 15 entries) plus a continuously-logged diagnostic block (`hub presence: stage=301 ... local id=<steamid>, N live slot(s), M avatar(s)`, with per-slot Steam ID / avatar pointer / world position / "pending" flag / raw bit-flags). A concrete self-healing mechanism is visible: `"member 2 (mode 1) is in this town (stage 301) but this machine had them in send group 04, corrected to ours, 01 (record word 00000410 -> 00000110)"`. This shows the mod detects when its internal bookkeeping of *which network "send group"/location bucket* a peer belongs to has drifted from reality, and silently patches the bitmask so the engine will actually spawn/render that peer. This is almost certainly why the FAQ insists **everyone** must enable "See the party in town" — a partial rollout would desync exactly this kind of bucket assignment.
- **Save safety & self-disable** — no hook names reference file I/O; the backup is simplest explained as a plain file-copy routine run once at loader init, not an engine hook, consistent with "never writes your save."
- **Quest classification at startup** — both logs dump the entire quest category table (*"522 quests in 42 type-flag group(s)"*, with bitmask groupings like `0x00001002`, `0x00081802`) immediately after joining a hub. This is very likely how the mod decides, per quest, whether cutscene-gate logic even applies (Assigned/Story quests only — see §5) versus Optional/Investigation/Arena quests that never had the restriction.

**What I could not verify:** the literal Steamworks function names used (inferred only); the exact mechanism for "Match the host's campsite" (the log shows a tracked `campsite field` value changing, but no dedicated "campsite" hook name appeared in the sampled excerpts — plausibly folded into the `prepare`/`set_pending_quest` pipeline); the "Use a voucher when joining" code path (not observed in the sampled log windows, default-OFF so less likely to appear in a typical 2-player session); and any detail of the panel's actual ImGui widget code (only the chrome — hotkeys, page cycling — is documented).

## 3. Changelog & known issues

This is the weakest-evidence section, and I want to be explicit about why: Nexus's **Changelogs** and **file-version history** are rendered as client-side widgets that the single archived snapshot did not capture (the raw HTML shows the literal heading "Changelogs" followed immediately by unrelated image content — the list itself never loaded server-side). What **is** independently confirmed: one upload (20 Sept 2026) and one update (21 Sept 2026, i.e., roughly a one-day hotfix cycle), a "Files 1" count (a single current archive, no retained old-version files listed separately), and public version label "1.2" vs. internal build "1.0.191.0" (§2). The **Bugs tab shows a count of 7** but, again, no individual bug titles/descriptions were recoverable from this archive.

In lieu of itemized bug reports, the mod page's own words are the most reliable signal of known weak spots: the explicit **testing-coverage disclaimer** that 3–4 player parties and **Iceborne** content "have had less coverage," and the FAQ's acknowledgment that automatic departure/join can be **delayed by an open menu** (a UX edge case common enough to warrant its own explicit callout and a 30-second auto-close timer for cutscene-watching specifically). The runtime logs independently surface one recurring, possibly-benign internal error: `"capture open failed: board-state11 error=5"`, logged repeatedly around every quest-board state transition in both sampled sessions — it never appears to block progress in these particular logs (the join completes seconds later both times), but a repeating non-zero error code in a hot path is exactly the kind of thing likely to surface as one of the 7 reported bugs in edge cases (e.g., slower machines, different quest types, 3–4 player lobbies).

## 4. Community reception

Press coverage was immediate and uniformly positive, framing the mod explicitly within the cross-game "Seamless Co-op" genre the user is drawing inspiration from. **DSOGaming** ([dsogaming.com, Sept 2026](https://www.dsogaming.com/mods/monster-hunter-world-seamless-co-op-mod-released/)) summarized the vanilla pain point plainly: *"Players would launch a quest, watch a cutscene and the game would notify the host that they can now fire an SOS Flare. Alternatively, one player could leave their quest, go back to the base, and join the other player's active quest via the quest board."* — and explicitly lists it alongside Seamless Co-op mods for Dark Souls Remastered/2/3, Elden Ring, Armored Core 6, Lies of P and others, i.e., trade press immediately recognized this as the same genre as the user's stated inspirations. **Dualshockers** (published 2026-09-23, [dualshockers.com](https://www.dualshockers.com/new-monster-hunter-world-mod-completely-overhauls-co-op-mechanics/)) called it *"Jolly Cooperation"* and was unusually specific about the vanilla flow it replaces: *"requiring everyone in the same lobby[...] to start the story quest individually, to see the monster's introduction cutscene, and then for all but one player to leave the quest and join the final member's instance[...] This was previously convoluted, especially with the unskippable cutscenes World is infamous for."* Tellingly, the same article notes in passing that *"Wilds may have its own buggy form of shared worlds"* — an early, informal signal (not a primary source, flagged as such) that Wilds' native multiplayer, while improved, is **not considered problem-free by outside observers either**, reinforcing the opportunity for a Wilds-focused mod.

Direct, verifiable **user** sentiment was harder to obtain — Reddit blocked both `reddit.com/.json` and `old.reddit.com` search/listing endpoints with forced login redirects in every attempt, confirming the task's access-notes warning; the `pullpush.io` mirror API worked intermittently (rate-limited at 429 on repeated calls) and did not surface a dedicated release-announcement thread in the sampling window available. It did, however, surface one organic, independently valuable data point: a real r/MonsterHunterWorld troubleshooting post (`reddit.com/r/MonsterHunterWorld/comments/1wyvhkb/`, retrieved via pullpush) from a player debugging an unrelated NPC-interaction issue who states *"The only mod I have is Seamless Coop, but even after removing it didn't solve my problem,"* — direct evidence of organic, already-in-progress real-world adoption of the mod outside of press coverage, consistent with the 146 Posts / 7 Bugs engagement numbers on the mod page itself. Beyond that, general reddit-sentiment summaries returned by search tooling (not independently verified against raw threads, and flagged here as **lower-confidence, synthesized** rather than directly quoted) describe a consistent theme of *"finally, someone fixed MHW's multiplayer"* framing and requests that Capcom "make it official" — directionally plausible given the press tone and the sheer post count, but I cannot cite specific usernames or verbatim Reddit text for this sentiment the way I can for the Steam Community and press sources above.

No direct evidence of a "please port this to Wilds" thread was found in the time available; this should be treated as an evidence gap rather than a negative finding (see §9).

## 5. MHW vanilla story multiplayer rules & complaints

**The core mechanic (confirmed across Fextralife, Steam Community, and press sources).** Monster Hunter World's multiplayer gate applies specifically to **Assigned Quests** (the main story line) and some **Special Assignments**: every participating player must individually reach and watch (or sit through) the quest's monster-introduction cutscene before that quest becomes joinable by others — via quest-board listing or **SOS Flare**. The practical workaround players converged on: everyone starts the story quest **solo**, watches the cutscene, then all but one player chooses "Return from Quest" (never "Abandon," which can forfeit the watched-flag) so that one remaining player can be joined by the others. **Optional Quests, Investigations, and Expeditions have no such gate** and can be formed as a party from the quest board before departure (Fextralife, [monsterhunterworld.wiki.fextralife.com/Multiplayer](https://monsterhunterworld.wiki.fextralife.com/Multiplayer)). Multiplayer also scales monster HP (~150% for 2 players, ~220–260% for 3+), a detail orthogonal to the join-gate but relevant context for why players *want* to be together from the start rather than solo-grinding the opener.

**Direct player quote (Steam Community, dated 1 May 2020 — [steamcommunity.com/app/582010/discussions/.../2261314050772177356](https://steamcommunity.com/app/582010/discussions/0/2261314050772177356/)):** *"I had to sit through a really slow boring series of cutscenes [...] I see I skip cutscene button but when I press it, it just brings me back to chapter selection."* This thread (10 replies) is a verified, dated, user-authored complaint specifically about cutscene friction, independent of any mod discussion.

**Capcom's later tweaks.** I found no evidence, in patch notes or secondary sources, that Capcom ever removed or loosened the assigned-quest cutscene gate itself across MHW's live service life; the one confirmed multiplayer-adjacent balance change was the **"two-player difficulty" added in patch 6.02** (Fextralife), which is an HP/difficulty-curve change, not a join-rule change. This "no official fix, ever" framing should be treated as **moderate confidence** — it rests on secondary/synthesized sourcing rather than a verbatim patch-note citation I could independently open, and is flagged accordingly (see §9).

**Monster Hunter Wilds inherits essentially the same rule — this is the most important finding for the user's project.** Multiple independent, directly-fetched sources from Wilds' actual launch week confirm the gate persists in the newest game:
- **Game8**, *Multiplayer Story: How to Play Campaign Co-op* ([game8.co/.../502807](https://game8.co/games/Monster-Hunter-Wilds/archives/502807)): *"Everyone must watch or skip the cutscene to progress and anyone who hasn't watched a specific cutscene from before that quest won't be able to join so it's important for everyone's campaign progress to be the same."*
- **Steam Community** discussion thread dated **28 Feb 2025** (launch day), [steamcommunity.com/app/2246340/.../596268022048594733](https://steamcommunity.com/app/2246340/discussions/0/596268022048594733/) — user "Val": *"having to do the solo stuff is a deal breaker for them [my partner]"*; user "MoXy69" replying: *"you both watch the cutscene a[t] the same time, whoever load[s] the quest first become[s] a party leader and automatically invite[s] everyone in [the] link party [...] If you don't like how World[']s multiplayer system [works], you[']re not gonna like this one either. Its better, but still confusing for some people."* This is a direct, dated, player-authored confirmation that the restriction and the confusion around it both survived into Wilds largely intact — Wilds' improvement is that the **Link Party auto-invites on quest post** once everyone has independently cleared the gate, removing the old "fire an SOS/browse the board" step, but **not** the requirement that every player individually reach the cutscene first.
- **Official Steam Community Guide** ([steamcommunity.com/sharedfiles/filedetails/?id=3435493455](https://steamcommunity.com/sharedfiles/filedetails/?id=3435493455)) confirms multiplayer itself is locked out entirely for roughly the game's first hour, until the player's tent-visit cutscene at the first base camp completes.
- **Game8**, *Link Members Explained* ([game8.co/.../499975](https://game8.co/games/Monster-Hunter-Wilds/archives/499975)): Link Party is capped at **4 players**; its "Environment Link" free-roam mode explicitly **refuses to open** between players at different story points ("to prevent players who haven't completed certain chapters from gaining an unfair advantage"), i.e. Wilds has *added a second, harder gate* (progress-parity for open-world roaming) on top of the inherited cutscene gate.

In short: the exact friction the proposed Wilds mod targets is **not hypothetical** — it is reproduced, confirmed, and complained-about in Wilds on day one, in nearly the same shape as in World seven years earlier.

## 6. Related MHW / MH Rise multiplayer mods (with source + hooked types)

**MHW — "Skippable Cutscenes" lineage (closed-source original, open-source revival).** The original *Skippable Cutscenes* mod (Nexus ID 5540) was built by **Moonbunnie**, published by **Tsulin/AsteriskAmpersand** under the **Iceborne Community Edition** banner, and is explicitly **closed/non-redistributable**. Its known flaw — it could **disconnect the player from their online session** when used — motivated a from-scratch, clean-room reimplementation: **[richardcassola/mhw-skippable-cutscenes](https://github.com/richardcassola/mhw-skippable-cutscenes)** ("Revival," open source, MIT-style). Its README documents genuinely useful low-level technique: it requires **Stracker's Loader** (the de facto MHW plugin host, `nexusmods.com/monsterhunterworld/mods/1982`), patches two signature-scanned functions it calls `execute_skip (P1)` and `show_prompt (P2)`, and flips a struct flag at offset **`+0x4D3`** to mark a cutscene skippable. Critically, it documents **six operating modes (E0–E6)**, discovered through iteration: `E0` mimics the original mod's behavior but leaves cutscene audio orphaned (the original's actual bug); `E6` additionally calls the game's own audio-stop functions (`STOP_EVCSKIP_EVC<nnnn>`/`_BGM`) and is the first mode to fix the audio-desync complaint; `E1` cleared the game's own gallery-replay flag and consequently misrouted the player to the cutscene gallery instead of back into gameplay; every injecting mode **re-verifies a unique byte signature and expected function prologue before patching** and logs "não implementado"/aborts cleanly if the build doesn't match — precisely the kind of defensive, signature-gated patching strategy huntardy's mod appears to also use (§2), and a strong, concrete pattern worth copying regardless of target game. Crucially, this project's README states outright that **no prior MHW mod ever reliably achieved "skip the cutscene and stay in the online session"** — confirming huntardy's Seamless Co-op is solving a problem the community had tried and failed to solve piecemeal for years.

**MHW — Iceborne Community Edition (ICE).** A large, actively maintained, **fully open-source** overhaul, [github.com/AsteriskAmpersand/Ice-Stable](https://github.com/AsteriskAmpersand/Ice-Stable). Relevant excerpts from its README: it ships its own "cutscene skip option [...] enabled on most cutscenes," caveated as *"still a work-in-progress feature. Some cutscene audio might not skip correctly"* — i.e., the same audio-desync problem independently acknowledged here too. For multiplayer, ICE takes a segregation approach rather than a bypass approach: *"While ICE is installed and enabled, hunters will only be matched with other ICE hunters. This is true when using matchmaking to find sessions or when creating/joining SOS."* ICE does **not** attempt to bypass the assigned-quest join gate itself — it is a general gameplay rebalance, not a co-op-flow fix — but its segregated-matchmaking design and WIP cutscene-skip are useful prior art on the *risks* of touching cutscene/audio systems.

**MH Rise — "Better Matchmaking"** by GreenComfyTea, open source MIT, [github.com/GreenComfyTea/MHR-Better-Matchmaking](https://github.com/GreenComfyTea/MHR-Better-Matchmaking) (Nexus: `monsterhunterrise/mods/1044`; requires REFramework ≥ v1.617). This is the most directly useful source artifact found for this project because **MH Rise and MH Wilds share the RE Engine + REFramework stack** (confirmed: REFramework targets RE Engine titles only — Resident Evil 2/3/4/Village, DMC5, MH Rise, and by extension Wilds — and explicitly **not** MHW's MT Framework). Its `timeout_fix.lua` ([raw](https://raw.githubusercontent.com/GreenComfyTea/MHR-Better-Matchmaking/cccd0ab8a51452effb131aab77f9e7147b37e0f6/reframework/autorun/Better_Matchmaking/timeout_fix.lua)) resolves and hooks the managed type **`snow.SnowSessionManager`** by name via `sdk.find_type_definition`/`get_method` — exactly the clean, reflection-based alternative to huntardy's raw-offset approach — and hooks a family of matchmaking-request methods: `funcOnTimeoutMatchmaking`, `reqMatchmakingAutoJoinSession`, `reqMatchmakingAutoJoinSessionRandom`, `reqMatchmakingAutoJoinSessionHyakuryu`, `reqMatchmakingAutoJoinSessionRandomMasterRank`, `reqMatchmakingAutoJoinSessionRandomMystery`, and `reqMatchmakingAutoJoinSessionRandomMysteryQuest`. Its technique: cache the arguments of whatever matchmaking call the player last made, then on the engine's own 60-second timeout callback, **silently re-invoke the identical native call** rather than giving up — a direct template for a Wilds auto-rejoin/auto-retry feature. Sibling files in the same repo (`region_lock_fix.lua`, `language_filter_fix.lua`) attack other multiplayer friction (region/language filtering blocking matchmaking) via the same singleton. Its own forum ecosystem shows unmet demand for exactly the user's goal: a Nexus forum thread titled **"[Mod Request] Village Quests allowed for multiplayer"** (forums.nexusmods.com/topic/11938918, inaccessible for direct quoting — 403 — but surfaced via search) indicates Rise players have explicitly asked for solo/story-quest multiplayer and that **no such mod has shipped for Rise either**, as of this research.

**MH Rise — `snow.QuestManager` structural reference.** [dtlnor/dtlnor-ref-mhrsb-scripts](https://github.com/dtlnor/dtlnor-ref-mhrsb-scripts), `autorun/no_side_monster.lua`, is not a multiplayer mod (it strips side-monsters from Arena quests) but is a clean, verified example of walking **`snow.QuestManager`**'s managed fields via REFramework: `sdk.get_managed_singleton("snow.QuestManager")` → `_normalQuestData`/`_DlQuestData` arrays → per-quest fields `_QuestNo`, `_MapNo`, `_BossEmType`, `_BossSetCondition`, `_SwapSetCondition`, etc. This confirms `snow.QuestManager` is the canonical RE-Engine quest-database singleton across Rise (and by strong architectural continuity, likely Wilds), complementary to `snow.SnowSessionManager` for session/matchmaking concerns.

**Net read for the project:** the *specific* feature combination the user wants (bypass the story cutscene gate **while staying in the same online session**, auto-join, auto-departure, shared town presence) has **no prior open-source implementation for any Monster Hunter title** — MHW's version is closed-source, Rise's modding community solved *adjacent* matchmaking pain (timeouts/region/language) but not the story-gate itself, and the one MHW mod that tried pure cutscene-skipping has a documented history of breaking online play. This is a genuine gap, not a reinvention.

## 8. Key takeaways for the MH Wilds Seamless Co-op project

1. **The core problem is proven to still exist in Wilds**, verified via day-one player testimony (§5) — this is not a stale MHW-era complaint being retrofitted onto a game that already fixed it. The project's central premise is sound.
2. **Build on REFramework's managed/reflection API, not raw signature scanning.** MHW forced huntardy into fragile, offset-based MinHook detours (`MHW+0x25C348`-style) because MT Framework has no public modding API. Wilds, like Rise, exposes `sdk.get_managed_singleton("snow.QuestManager")`, `snow.SnowSessionManager`, and friends by name (§2, §6) — a dramatically more maintainable foundation, and one with an existing community (`praydog/REFramework`) and directly relevant prior art (`GreenComfyTea/MHR-Better-Matchmaking` already hooks the session/matchmaking singleton for a cognate purpose).
3. **Communicate through Steam Lobby (and likely lobby-member) data, not a custom protocol** — this is the single clearest, best-verified architectural lesson from the gist logs (`published coop_post="<lobbyid>;<timestamp>"`, "peers: N in the session, N running the mod"). Riding the game's own existing network/session layer rather than building parallel P2P code is both lower-risk and exactly what the FAQ independently claims ("uses the game's existing quest systems and Steam lobby features").
4. **Expect "See the party in town" to be mostly free** in Wilds given its native lobby/open-world design — redirect the engineering effort MHW had to spend on hub-presence bookkeeping (§2's bitmask "send group" correction logic) toward the cutscene-gate and auto-accept problems instead, which remain unsolved in Wilds.
5. **Treat the cutscene-skip-vs-online-session trade-off as a known hazard, not a hypothetical one.** Two independent MHW projects (the original Skippable Cutscenes mod and its open-source Revival) document real, hard-won lessons here: disconnect risk, orphaned audio, misrouted post-cutscene state — and the Revival's signature-verify-before-patch discipline (abort cleanly, log why, never guess) is directly worth adopting.
6. **Build in a self-disable/version-mismatch system from day one**, modeled on huntardy's "MOD DISABLED" + reason, given how version-sensitive this class of mod is.
7. **Scope early testing honestly.** Even huntardy's mature, late-iteration (v1.2) MHW release explicitly limits its own confidence to 2-player groups and flags 3–4 player and expansion content as under-tested — set the same expectation for an initial Wilds release rather than promising full-party reliability immediately.
8. **Wilds adds a harder, second-order gate (Environment Link's progress-parity check) that MHW never had** — any Wilds seamless-co-op design should explicitly decide how it interacts with (or deliberately bypasses) this story-progress-equality requirement, since it's new ground relative to every prior-art mod surveyed.

**Joining & departure**
- 1.2: bypassing the gate on the quest board was not enough — a second check on the departure screen also had to be bypassed.

**Cutscenes**
- Cutscene sync was **removed for Expeditions** in 1.2 because each player's own quest script runs story events locally —
  mirroring the host's caused phantom monsters and premature "seen" flags. Later versions re-added it carefully.
- A shared cutscene is verified to be **the same cutscene on both PCs (by identity, not just number)** before playing.
- **Vote-to-skip**; when skipping, the game is run fast so everything the cutscene sets up still happens; audio/music
  edge cases (orphaned voices, music lost) took several releases to get right.
- Avoid double playback when a follower later reaches the same trigger; restore the hunter's position after replays;
  black-screen and fall-through-ground fixes after shared cutscenes.
- 1.6: a story cutscene plays for everyone **whoever triggers it** (not only the leader).

**World/NPC/prop state**
- 1.3–1.6: NPCs, escort carts, props, story monsters, voiced pop-ups, camera sweeps (within 25 m of leader) and
  area banners are **driven by the leader's quest** so everyone sees the same thing; late joiners get NPCs placed where they
  are on the leader's screen; from then on the story advances for everyone when **any** player reaches the trigger.

**Story progression ("Follow the leader's story")**
- Records the leader's story steps on the follower's save **through the game's own routines**, only forward, only when
  stories are close (≤3 assignments apart); never while in conversation/menus (that soft-locked a player).
- Needed follow-up fixes for: Hunter/Master Rank catch-up, first-clear rewards (e.g. Vitality Mantle), optional quests the
  leader's save unlocked, per-player collectibles (Grimalkyne gadgets must stay per-player), side quests stay personal,
  research progress sharing, retrying failed quests not replaying first-time cutscenes.
- Users still hit **progress-flag desync / soft-locks**; one user **hard-locked their save by joining "future" story quests**
  (author: "Joining future quests isn't intended and breaks progression" → restore backup). ⇒ Enforce progress bounds.

**Save safety**
- Backups at launch (10 kept); **save on returning to town** (the game doesn't autosave there, so co-op progress was lost on close);
