**Research window:** live GitHub code/repo search + web/Wayback fetches performed 2026‑10‑20. All dates below are as cited in source material; where a source carries no date, that is noted.

## 1. REFramework for Wilds (status, APIs, dumping, limits)

**Status (verified).** REFramework moved to a **monolithic build model**: a single `REFramework.zip`/`dinput8.dll` now auto‑detects the running RE Engine title and dispatches to the correct type‑database (TDB) layout, replacing the old per‑game zips (`MHWILDS.zip` etc.). Monster Hunter Wilds is explicitly listed as a supported game alongside DMC5, RE2/3/4/7/8/9, MHRise, MHStories3, SF6, DD2, Pragmata, and the Mega Man Star Force Legacy Collection (`praydog/REFramework-nightly` releases page, fetched 2026‑10‑20; `praydog/REFramework:README.md`). Install is still "extract only `dinput8.dll`" for non‑VR use; a separate `csharp-api.zip` is required only for the **C# plugin runtime**, and nightly text explicitly states **"stable releases do not include .NET support"** — i.e., C# plugin development (and tools built on it, see §4) requires a **nightly** build (`praydog/re-engine-mcp:README.md`).

**Breakage after title updates (verified, with examples).** `praydog/REFramework` has open issues specific to MH Wilds title updates: **#1292 "MHWilds TU1 Crash"** (filed 2025‑04‑04, random crashes "after title update") and **#1488 "REFramework crashing MHWilds during initialization"** (filed 2025‑12‑30, still open as of last update 2026‑01‑02). More concretely, `src/mods/IntegrityCheckBypass.cpp` embeds a literal version‑tagged byte‑signature comment — `"...", // MHWILDS v1041/MHSTORIES3` — proving the maintainers track and re‑signature specific MH Wilds build numbers (here "v1041") when Capcom's obfuscated code shifts. This is the clearest direct evidence of *how* title updates break REFramework: byte‑pattern scans (not stable function tables) locate anti‑tamper hooks and pak‑loading code, and those patterns can silently stop matching after a patch until a maintainer re‑derives them.

**TDB/runtime quirks that matter for native/C++ work (verified).** `shared/sdk/GameIdentity.hpp` exposes `is_mhwilds()`, `is_re9()`, `is_dd2()`, `tdb_ver()`. `shared/sdk/REType.cpp` and `RETypeLayouts.hpp` hard‑code that **MH Wilds (like RE9 and DD2) uses a `0x68`‑byte `REType` struct with shifted pointers**, vs `0x60` for RE8‑era games — a maintenance "footgun" per the source comment, and a concrete trap for anyone hand‑rolling native structure offsets instead of using the SDK.

**Dumping the Wilds type database (verified mechanism).** The in‑game **Object Explorer** (Developer Tools) has a **"Dump SDK" button** that spawns `ObjectExplorer::generate_sdk()` on a background thread and writes `il2cpp_dump.json` via `REFramework::get_persistent_dir(...)` (`praydog/REFramework:src/mods/tools/ObjectExplorer.cpp`). A direct code comment in `IntegrityCheckBypass.cpp` confirms: *"function names can be found within il2cpp_dump.json, which is dumped with REFramework's 'Dump SDK' button in developer mode."* The generated native C++ headers that `shared/sdk/ReClass.hpp` and `REManagedObject.hpp` `#include` — **`Enums_Internal.hpp`, `RETypes.hpp`, `REType.hpp`** — are exactly the kind of file the user's game folder shows; this strongly indicates the local install has run (or REFramework auto‑generated) an SDK dump for native‑plugin compilation. The full pipeline for *native (`via.*`) type* layouts (as opposed to managed `app.*` types, which `il2cpp_dump.json` already captures) is documented in `reversing/rsz/readme.md`: dump the exe with x64dbg's Scylla → run REFramework's SDK dumper → run `emulation-dumper.py` (Unicorn CPU emulation of RSZ deserializer chains) → run `non-native-dumper.py` to merge native + non‑native layouts into `rsz<postfix>.json`. A pre‑built `reversing/mhwilds.rcnet` (74,833 bytes) ships in the repo as the Wilds RSZ reference used by `alphazolam/RE_RSZ`'s 010 Editor template (README confirms "Monster Hunter Wilds" in its supported‑games list).

**Lua API (verified against docs + real mod code).** `cursey.github.io/reframework-book/api/sdk.html` and `/api/re.html` (fetched 2026‑10‑20) confirm every primitive named in the task: `sdk.get_tdb_version`, `sdk.get_native_singleton`/`sdk.get_managed_singleton` (Object Explorer's "Native Singletons"/"Singletons" views list valid names), `sdk.find_type_definition`, `sdk.create_instance`, `sdk.call_native_func`, `sdk.hook(method_def, pre_fn, post_fn, ignore_jmp)` with `sdk.PreHookResult.SKIP_ORIGINAL`/`CALL_ORIGINAL`, `sdk.deserialize` (parses raw RSZ bytes, e.g. from a `.scn`), `sdk.hook_vtable`. `re.on_frame`, `re.on_draw_ui`, `re.on_application_entry(name, fn)` (valid names enumerated from `via.ModuleEntry`, including `InitializeNetwork`, `SetupNetwork`, `StartNetwork`, `InitializeVoiceChat`, `InitializeVivoxlib` — the last implying Vivox is at least present in the engine's generic module list, separate from PlayFab), `re.on_script_reset`, `re.on_config_save`, `re.on_pre_gui_draw_element`. Real Wilds mods confirm these work exactly as documented — e.g. `kmy0/BetterSoS` uses `sdk.PreHookResult.SKIP_ORIGINAL` to intercept the SOS search button (`reframework/autorun/BetterSoS/better_sos/hook.lua`), and `WetU/MHWs_REF_Scripts` uses raw `sdk.find_type_definition(...):get_method(...):call(...)` chains throughout. `imgui`, `json.dump_file/load_file`, and `re.on_config_save` are all used in production (`HolographicWings/MHWilds-Mod_Lite-Environment:reframework/autorun/lite_environment.lua`).

**Limits (verified/observed).**
- **Networking from Lua is not exposed as a first‑class API** — no `sdk`/`re` function wraps sockets or the game's network stack directly. All "networking" mods (BetterSoS, HuntDumper) work by calling the **game's own managed methods** (`app.NetworkManager`, `app.NetworkRequestManager.searchSession/joinSession`) through `sdk.call_native_func`/`:call(...)`, i.e., riding the game's existing P2P/session plumbing rather than opening independent connections.
- **Native function hooking has caveats**: the docs explicitly warn *"Some native methods may not be able to be hooked with this [`sdk.hook`]... if they are just a wrapper over the native function"*, requiring extra framework‑side work.
- **C# plugin support (used by `re-engine-mcp`, see §4) only exists in nightly builds**, not the last "stable" release.
- REFramework ships an **"Integrity Check Bypass"** mod (on by default) that actively patches anti‑tamper code (see §2) — this is itself evidence that running any REFramework build at all already requires defeating Capcom's obfuscated protections, which is relevant risk context for a co‑op mod built on top of it.

## 2. Protection / anti-cheat / ban risk / Capcom stance

**DRM.** Community sources (insider‑gaming.com, Sportskeeda, GameSpew, all undated‑but‑launch‑era 2025) report **Denuvo Anti‑Tamper on the PC build at launch (2025‑02‑28)**. PCGamingWiki has a Monster Hunter Wilds page (RE Engine/Capcom infobox confirmed via fetch 2026‑10‑20) but its DRM/anti‑cheat bullet detail did not render cleanly through my fetch tool — treat the Denuvo claim as community‑sourced rather than a clean primary quote, pending direct confirmation.

**Capcom's official stance (verified via secondary reporting of primary posts).** Per Game8 (`game8.co/games/Monster-Hunter-Wilds/archives/526805`, "Are Mods Bannable?"): Capcom posted on its official X account that cheating or "unauthorized modifications" result in **penalties including account suspension**; Capcom also said it would improve **filtering of modded quests so they no longer appear at the Quest Counter**, and accepting one anyway now throws an error; and that using mods to access **unreleased content** is itself considered cheating. Independent press (gaming.news 2025‑03‑17 "Capcom Permanently Bans Monster Hunter Wilds Modders from Multiplayer"; PCGuide (x2); VideoGamer; ComicBook) corroborates real **permanent multiplayer bans**, concentrated around reward/DLC‑unlock‑style mods following Title Update 1 (~March 2025). I could not reach Capcom's own `monsterhunter.com/eula/wilds/...` page (HTTP 403); the Steam storefront mirror of the EULA (`store.steampowered.com/eula/2246340_eula_0`) was readable and establishes a **revocable, non‑commercial license** (Art. 1) and mandatory **third‑party‑platform authentication** (Art. 4), but the portion I could read did not contain an explicit "no modding" clause in so many words — Capcom's enforcement appears to be driven by separate anti‑cheat/ToS statements (the X posts above) rather than a single quotable EULA line.

**Technical anti‑tamper internals (verified, from `praydog/REFramework:src/mods/IntegrityCheckBypass.cpp` — this is the single richest source found for this question):**
- **`fix_virtual_protect()`** hooks the WinAPI `VirtualProtect` via MinHook, backed by a **pristine cached copy of `ntdll!NtProtectVirtualMemory`** captured before anything else can tamper with it (`setup_pristine_syscall()`). On every call it diffs the live syscall stub against the pristine copy and **self‑heals** it if modified. The log lines this prints — `"[IntegrityCheckBypass]: Hooked VirtualProtect!"` — are *exactly* what the user's own REFramework log shows, confirming this code path is actively engaging on the local install.
- **`hook_add_vectored_exception_handler()`** (active when `tdb_ver() >= 73`, which covers MH Wilds) hooks `AddVectoredExceptionHandler`, and **`init_anti_debug_watcher()`** runs a background watcher (`tdb_ver() >= 74`).
- A routine named `immediate_patch_dd2()` (legacy name; its outer gate is `tdb_ver() >= 74`, shared by `is_mhwilds() || is_re9() || is_dd2()`) contains an **`is_mhwilds()`‑specific block** that locates a **"crasher_fn"** via `QueryPerformanceFrequency`/`QueryPerformanceCounter` import references, then patches a `cmp`/`jz` inside it and nukes (patches to `ret`) a companion **"scanner_fn"**. The code comments (written for the DD2 case, architecturally identical) explain the payoff: the obfuscated scanner runs **every frame**, and on detecting tampering it **corrupts renderer state so the crash looks like a GPU/DXGI‑present error** rather than an obvious anti‑cheat trip. The same function also hooks DirectX12 **`createBLAS`** (ray‑tracing acceleration structure creation) and locates a `corruption_when_zero` pointer, tying anti‑tamper health to the ray‑tracing pipeline.
- **PAK‑level integrity**: functions named `get_pak_flags`, `sha3_rsa_code_midhook`, and `restore_unencrypted_paks` strongly imply individual PAK entries carry **SHA3/RSA‑based signing/encryption flags** that the engine validates at load time, separate from the in‑memory scanner above.
- **Loose‑file‑loading block**: the code scans the executable for the literal path substring `"/natives/"` and reports *"the game explicitly looks for this string in the path and causes load failures if it finds it"* — i.e., Capcom's engine **actively detects and refuses the classic RE‑Engine loose‑file mod technique**, and REFramework neutralizes it by corrupting one character of the embedded string via a `VirtualProtect`+write. **Caveat:** this specific log path is explicitly labeled "(DD2)" in the source; I could not independently confirm the same string‑patch is wired up and exercised for the MH Wilds binary specifically (vs. only compiled for the DD2 branch of the same function) — flagged as moderate‑, not high‑, confidence for Wilds.
- Separately, REFramework also implements its **own loose‑PAK loader** (`ENABLE_PAK_DIRECTORY_LOAD`, compiled in whenever `tdb_ver() >= 81`, which covers the Wilds TDB) that hooks the DirectStorage pak‑open call and `CreateFileW` to let `.pak` files dropped in a configurable directory be injected — this is the `MHWILDS v1041` pattern mentioned in §1, and ships a UI toggle ("PAK Directory Loading", `on_draw_ui()`).

**Net assessment for risk:** Capcom has both the *capability* (frame‑by‑frame memory scanner + file‑signing checks) and the *demonstrated willingness* (real bans, March 2025) to act against client tampering, but enforcement so far has targeted **reward‑inflation / unreleased‑content / quest‑tampering** mods, not QoL/graphics/UI‑only mods (REFramework itself, and dozens of Lua autorun scripts cited below, operate in the open on Nexus without reported mass bans). A seamless‑co‑op mod that **changes session/quest‑join and cutscene‑playback behavior for all party members simultaneously** sits closer to the risky category than a solo HUD tweak, because it visibly alters online quest flow — this should be treated as a real, non‑zero ban‑risk factor, not just an anti‑cheat engineering problem.

## 3. Networking stack

**Crossplay/account layer (verified, community/official‑support aggregation via web_search of `monsterhunter.com/support/wilds/faq`, `iscrossplay.com`, Game8, chaosboost.com).** Full crossplay across PC/PS5/Xbox Series X|S; a **Capcom ID is required only for cross‑platform social features** (crossplay invites, cross‑progression) — not for base single‑platform play; toggled from the title screen only (not mid‑session); "Link Party" is the official name for a persistent cross‑platform friend group; lobbies reportedly hold up to 100 players with 4‑hunter hunting parties.

**In‑engine session architecture (directly verified from RE Engine type dumps — this is the key architectural finding for the project).** `app.net_session_manager.SESSION_TYPE` is a concrete enum with exactly six values (`kmy0/BetterSoS:typedef/ace/enums/app.net_session_manager.SESSION_TYPE.lua`):
```
0 NONE, 1 LOBBY, 2 QUEST, 3 LINK, 4 MEMORIES, 5 LOCAL
```
`app.NetworkManager : ace.GAElement` exposes `get_RequestManager()→app.NetworkRequestManager`, `get_UserInfoManager()→app.Net_UserInfoManager`, `get_ErrorManager()→app.NetworkErrorManager`. `app.NetworkRequestManager` carries a `_QuestSession` field of type `app.net_quest_session.cQuestSession` (itself `: app.net_session_manager.SessionManager`) and exposes **`checkOffline`, `searchSession`, `joinSession`, `leaveSession`** — each parameterized by `SESSION_TYPE` (`kmy0/BetterSoS:typedef/ace/app.lua`). `app.Net_UserInfoManager.getHostUserInfo(SESSION_TYPE)` returns an `app.Net_UserInfo`/`app.Net_QuestUserInfo`, the latter exposing `get_KeepQuestData()→app.cKeepQuestData` for in‑progress Expedition/Investigation persistence (confirmed live usage in `kmy0/BetterSoS:reframework/autorun/BetterSoS/better_sos/routine_search.lua`, which is, to date, the single richest piece of public source code showing a full quest‑join network handshake — see §4/§7).

This directly explains the vanilla "join only once the hunt starts" behavior the project is working around: the **QUEST session type is what BetterSoS's SOS/auto‑join flow targets** (`searchSession(SESSION_TYPE.QUEST, ...)`, `joinSession(SESSION_TYPE.QUEST, cJoinQuestSessionInfo, ...)`), and a QUEST session only exists once `app.cQuestDirector.acceptQuest(...)`/`goQuest(...)` has actually been invoked for a hunt. The pre‑hunt walk/investigation/cutscene segment of a story mission almost certainly runs the party inside the **LOBBY** and/or **LINK** session layers instead (official docs' "Link Party" concept maps naturally onto `SESSION_TYPE.LINK`), with no QUEST session yet open for others to join into. **MEMORIES** and **LOCAL** values are enumerated but their runtime semantics are *not* documented anywhere found in this research — flagged as an open question (MEMORIES plausibly relates to MH Wilds' cutscene‑replay/"Memories" viewer, but this is inference, not verified).

**Quest search/join data shapes (verified, full field dump from `kmy0/BetterSoS:typedef/ace/app.lua`):** `app.net_session_manager.SessionManager.cSearchResultQuest` carries `questId`, `memberNum`/`maxMemberNum`, `isLocked`, `isAutoAccept`, `startedAt`/`acceptedAt`, `fieldId`, `questLevel`, `targetMonster`, `questSessionId` (string), `questType`, `campList`, `isBoost`, `envType`, `questTimeLimit`, `questRank`, **`multiplaySetting` (typed `app.net_quest_session.cCreateQuestSessionInfo.MULTIPLAY_SETTING`** — an enum almost certainly encoding "friends‑only/anyone/solo" visibility, directly relevant to how a seamless‑join mod should represent itself), and `hunterInfo[]` (`hr`, `weaponType`, `reserveWeaponType`, `ishost`). Joining constructs an `app.net_quest_session.cJoinQuestSessionInfo : app.net_session_manager.cJoinSessionInfo` via `.ctor(sessionId:String, isRescue:Boolean, questId:Int32, hostId:Guid, password:String)`.

**Quest‑data sourcing branches at join time (verified, `routine_search.lua:_start_quest`)** — important because a seamless‑join mod must handle all three: if the host's `Net_QuestUserInfo.get_KeepQuestData()` is non‑null, the client builds an `app.cActiveQuestData` via `.ctor(app.cKeepQuestData)` (**Investigation/Expedition** path); otherwise it falls back to `app.MissionManager.getQuestDataFromMissionId(questId)` (**story/optional quest** path) and finally `app.MissionManager.getStreamQuestDataFromID(questId)` (**event/limited‑time quest** path).

**PartyWin.dll / PlayFab Party (unverified — explicit gap).** I found **no modder reverse‑engineering notes, GitHub repo, or RE Engine type dump anywhere that analyzes `PartyWin.dll` internals** or explicitly ties it to Microsoft PlayFab Party. The association is a reasonable inference from the filename and from PlayFab Party being a known Microsoft cross‑platform session/voice/relay product used by several crossplay titles, but this research could not find anyone in the public MH‑modding community who has actually probed it. This is a real research gap the project will need to close itself, likely by combining Object Explorer singleton browsing with `re.on_application_entry("InitializeNetwork"/"SetupNetwork"/"StartNetwork")` hooks.

**Confirmed adjacent manager:** `app.ChatManager` exists as a real managed singleton (`praydog/re-engine-mcp:reframework/plugins/source/TestWebAPI.cs`, gated `#if MHWILDS`, calling `API.GetManagedSingletonT<app.ChatManager>()`; identical code also lives in `praydog/REFramework:csharp-api/test/Test/TestWebAPI.cs`, proving it's an upstream‑maintained test, not a one‑off fork).

## 5. Tools & file formats

- **Fluffy Mod Manager** (fluffyquack.com) — the de‑facto PAK mod manager; per a Patreon changelog summary (`patreon.com/FluffyQuack`, not read directly, digested via search), Wilds support requires a **specific `.sub` pak naming scheme** and currently **one `.pak` per mod archive, no extra files** — a real packaging constraint for anything beyond a pure asset swap.
- **REFramework's own loose‑PAK loader** — see §1/§2: `ENABLE_PAK_DIRECTORY_LOAD`, a DirectStorage‑hook‑based alternative to Fluffy's approach, gated behind a `tdb_ver() >= 81` check that covers MH Wilds, with its own in‑game "PAK Directory Loading" UI toggle.
- **Type/SDK dumping chain**: Object Explorer "Dump SDK" → `il2cpp_dump.json` + generated C++ headers (`Enums_Internal.hpp` etc.) → `kagenocookie/REFDumpFormatter` ("Tool to convert REFramework il2cpp json dump into a more useful format (C# or lua)") produces the `.lua` `---@class` typedef trees seen throughout `kmy0/*` repos → optionally feeds `reversing/rsz/emulation-dumper.py` + `non-native-dumper.py` for native `via.*` RSZ layouts.
- **RE_RSZ** (`alphazolam/RE_RSZ`) — 010 Editor binary template for RSZ‑bearing files (`.scn/.pfb/.user/.rcol/.fsmv2/.motfsm/.bhvt`); explicitly supports MH Wilds; README now points users toward **REECE, REE‑Lib‑Resources, or REasy** for more current dumps.
- **kagenocookie/REE-Content-Editor ("REECE")** — actively developed (last updated 2026‑10‑21 at time of check), built on **`kagenocookie/RE-Engine-Lib`**; supports MH Wilds for most structured file types with a 3‑layer patch model (files → resource objects → entities) and bundle‑based mod merging so multiple mods can edit the same catalog file.
- **kagenocookie/ReachForGodot** — Godot‑based visual scene/RSZ data editor (sibling project).

## 7. Prior art for seamless/story co-op in Wilds

**The direct inspiration, confirmed in detail.** `huntardy`'s **"MHW Seamless Co‑op"** (Monster Hunter **World**, Nexus 8805, fetched via Wayback 2026‑09‑24 snapshot) is a **native `xinput9_1_0.dll` proxy‑loaded DLL** (not a REFramework Lua script — matches the user's brief), compatible with but independent of Stracker's Loader, with these confirmed features: **auto‑follow the host's quest; "Bypass the cutscene gate — ON" setting that explicitly lets joiners start a story quest before the leader reaches the normal multiplayer‑unlock cutscene; "Watch the leader's cutscenes — ON" to play the host's story cutscenes on followers' screens; match the host's chosen campsite; shared town presence in the hub; F10 "request join," F11 panel, F5/F2/F3 navigation hotkeys; a settings text file; per‑player mod‑version mismatch detection (highlighted red); self‑disabling with a stated reason on unsupported game builds; and an explicit no‑save‑write guarantee (rolling backups only).** It is actively maintained (last updated 2026‑09‑21 per Wayback) but has **no Wilds counterpart**.

**Status for MH Wilds specifically: no public mod exists.** Extensive GitHub code search (`sdk.find_type_definition` + Wilds‑identifying strings, `get_managed_singleton` scans, and direct repository search for "seamless"/"coop"/"co-op" combined with mhwilds/MHWS terms) turned up **no repository implementing cross‑quest‑session following or cutscene‑gate bypass for MH Wilds.** A Nexus Mods forum thread **"[Mod Request] Seamless Coop Mod" (MH Wilds subforum, started by a user named PsionPhoenix, reported August 2025)** exists per search‑engine indexing, expressing hope but doubting feasibility; I could **not** fetch its actual content directly (both a live fetch and a Wayback snapshot attempt returned 403/404), so this characterization is sourced only from aggregated search results, not a primary read — flagged as lower confidence.

**The closest existing public‑source analogue is *not* a seamless‑co‑op mod.** `kmy0/BetterSoS` automates the **existing, vanilla‑available** SOS/quest‑search‑and‑join flow (`SESSION_TYPE.QUEST`) — auto‑searching, auto‑picking, and auto‑joining rescue sessions faster than a human clicking through menus. It does **not** open a QUEST session earlier than vanilla, does not touch `app.DemoMediator` cutscene playback, and does not bypass any cutscene‑gate. This is an important distinction: **BetterSoS proves the join‑a‑quest‑session network call sequence in working, public code, but it operates entirely downstream of the exact barrier the user's project needs to remove.**

**Feasibility signal (inference‑level, synthesized from community discussion, not a verified technical audit):** the barrier is understood by at least some of the community to be **code‑level** (story quests gate the multiplayer‑invite option behind specific solo cutscene/FSM completion, not just a UI toggle), raising real risk of event‑trigger desync or softlocks if naively patched, compounded by the anti‑tamper risk discussed in §2. No modder has published a working counter‑example for Wilds to either confirm or refute this at the time of research.

## 8. Key takeaways for the MH Wilds Seamless Co-op project

1. **The architecture you need is named and enumerable right now.** `app.net_session_manager.SESSION_TYPE {NONE, LOBBY, QUEST, LINK, MEMORIES, LOCAL}` is a real, confirmed enum. Vanilla's "can't join until the hunt starts" behavior corresponds to **no QUEST session existing yet** for a story mission's walk/investigation/cutscene segment — the party is almost certainly only linked via **LOBBY**/**LINK** at that point. Your core technical task is best framed as: *either* force an earlier **QUEST** session open (mirroring the exact `app.NetworkRequestManager.joinSession(SESSION_TYPE.QUEST, app.net_quest_session.cJoinQuestSessionInfo, ...)` call `BetterSoS` already demonstrates, but triggered at story‑quest‑accept time instead of post‑hunt‑SOS time), *or* find and ride whatever presence/sync already exists at the **LOBBY/LINK** layer for the in‑hub "see your party" behavior the official docs describe, and layer quest‑join logic on top of that. Either path starts from `app.MissionManager.get_QuestDirector()` → `app.cQuestDirector.acceptQuest(cActiveQuestData, cQuestAcceptArg, …)` / `goQuest(...)`.
2. **Handle all three quest‑data sourcing branches**, not just story: `cKeepQuestData` (Investigation/Expedition), `MissionManager.getQuestDataFromMissionId` (story/optional), `getStreamQuestDataFromID` (event). `BetterSoS`'s `_start_quest()` is a working reference implementation of this branching logic.
3. **Cutscene sharing is a solved, documented sub‑problem.** `app.DemoMediator` is the real cutscene controller: `onPlayStart(ace.DemoMediatorBase.cParamBase)`, `get_CurrentTimelineEventID()`, `requestSkip()`, `notifyCutSkipEnd`, `unload()`, `endEndFsm(...)`. A working **auto‑skip** implementation already exists in public source (`WetU/MHWs_REF_Scripts:Auto_skip_cutscenes.lua`) keyed off a `TimelineEventDefine.ID` enum (field names like `evc0105`, `evc1002`). "Watch cutscenes together" is the *inverse* problem — instead of calling `requestSkip()` for everyone, you'd want to **mirror the host's `onPlayStartTimeline`/current‑event‑ID to joiners** and suppress their independent gameplay input during that window, which is architecturally adjacent to what `HolographicWings/MHWilds-Mod_Lite-Environment` already hooks (`DemoMediator.onPlayStart`/`unload` pairs) for a different purpose (GI/fog restoration).
4. **Don't confuse Capcom's own "seamless" terminology with yours.** `app.cQuestDirector.goQuest(is_seamless, skip_session, keep_stage, suppress_auto_save)`, `app.cQuestFlowParam.IsResultSeamless`, and `app.cGUIQuestResultInfo.getSeamlesResultListDispTime` all refer to **UI/loading‑transition smoothness** around quest start/end, not multiplayer join timing. Keep this distinction explicit in your own code comments so future contributors (or an LLM assistant) don't misinterpret dev‑code "seamless" hits as relevant hooks.
5. **Build as a REFramework `reframework/autorun` Lua mod (optionally backed by a C# plugin via the nightly + `csharp-api` path), not a from‑scratch native DLL.** REFramework already solves hot‑reload, hooking, ImGui UI, singleton/type access, *and* co‑exists with Capcom's anti‑tamper (it patches around it, see §2) specifically for MH Wilds, and the entire existing SOS/quest‑join/cutscene‑skip precedent (`BetterSoS`, `WetU` scripts, `HunterPie_Analytics`) is written this way. `praydog/re-engine-mcp`'s chain‑query pattern (`EnemyManager._EnemyList → Context → Em → Basic → IsBoss`) is also a genuinely useful *development accelerator*: it lets an AI‑assisted workflow interactively discover unknown fields/methods against a live game process instead of guessing from static dumps.
6. **The PartyWin.dll/PlayFab question is unsolved by the community and is now your team's job.** No existing public research explains whether LOBBY/LINK presence is P2P/host‑authoritative or relay‑routed through a Capcom/Microsoft backend — this materially affects whether early‑QUEST‑session‑opening would even be *accepted* server‑side for a party that hasn't reached the normal unlock point, versus being a purely client‑local gate.
7. **Treat ban risk as real but calibrated.** Enforcement to date has focused on reward/DLC‑unlock/quest‑tampering mods, not QoL/UI mods — but a mod that changes *multiplayer quest‑join eligibility for all participants* is closer to the former category than the hundreds of solo‑experience Lua scripts cited in §4. Plan for graceful self‑disable on unsupported builds (mirroring the MHW original's explicit "MOD DISABLED" messaging) and keep the mod's footprint client‑local/non‑save‑writing, as both `BetterSoS` and the MHW original already do.
